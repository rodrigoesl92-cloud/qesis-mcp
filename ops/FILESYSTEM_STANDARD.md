# QESIS+ filesystem standard

**v1.0 · 2026-08-28 · Authored by ARCHITECT under the filesystem mandate ratified 2026-08-14.**
**Gated by SENTINEL. Reviewed by COUNSEL. The operator is the sole approver of any move it proposes.**

This document says what belongs where, what is generated and what is written by
hand, how ops documents are named, and the one rule that makes a citation
falsifiable rather than decorative. It does not restate governance. Governance
lives in `sovereign-infra/ops/GOVERNANCE.md` and that document wins on every
point of conflict.

It exists because on 2026-08-14 a single session located the wrong path three
times in one day. The root cause was structural, not attentional. There was no
locator, so every session re-derived file locations by inference, and inference
about a filesystem is guessing with better grammar.

---

## 0. Retrieval order. Locked 2026-08-28 on the operator's instruction.

**Before anything else, including before the first deliverable, a session reads
the report set and knows exactly where the ecosystem stands.**

`SESSION_START.md` already orders `ops/PATH_REGISTRY.json`, then
`ops/ECOSYSTEM_STATE.json`, then `CLAUDE.md`. That set answers *where things
are* and *what the rules are*. It does not answer *what the last measured run
found*. The report set does.

| # | Read | Answers | Generated by |
|---|---|---|---|
| 1 | `ops/AUDIT_REPORT.md` | the full cross-repository verdict, with the command, the exit code and the deciding predicate on every row | `scripts/audit_ecosystem.py`, native |
| 2 | `ops/SELFHEAL_LATEST.json` | the hourly control set: verdict, degraded, benign, escalations, failed | `scripts/selfheal.py` |
| 3 | `ops/reports/<YYYY-MM-DD>.md` | the runner's daily narrative for one repository | `scripts/build_ops_report.py` under `daily-ops-report.yml` |
| 4 | `ops/CI_LAST_FAILURE.md` | the last real CI failure and its root cause | `scripts/ci_feedback.py` |
| 5 | `ops/PATH_REGISTRY.json` | where everything is | `scripts/build_ecosystem_state.py` |
| 6 | `ops/ECOSYSTEM_STATE.json` | what is true now | `scripts/build_ecosystem_state.py` |
| 7 | `data/DATA_MAP.json` | where every input actually is | `scripts/build_data_map.py` |
| 8 | `CLAUDE.md` | what the rules are | hand maintained, governed |

**Rule FS-0.** A session that states anything about ecosystem standing without
having read rows 1 to 4 has reasoned from a proxy. That is D-115 and it is the
single most expensive failure mode this ecosystem has recorded.

**Rule FS-0a.** `sovereign-infra/ops/reports/` under the **non-OneDrive** path
holds pointer files, not reports. They exist only to record that a scheduled
task was configured with the decoy path. Reading them as a report series is
L-143 repeating itself one level down.

## 1. The three roots, and why no two of them are the same kind of thing

Neither repository is complete alone, and the third root is not a repository at
all. Confusing these three is the origin of every path defect on the ledger.

| Root | Canonical path | Kind | Holds |
|---|---|---|---|
| `qesis-mcp` | `C:\Users\Lenovo\qesis-mcp` | public git repository | the served surface, the MCP server, the index artefact, the CI gates, the landing page, the generated ops artefacts |
| `sovereign-infra` | `C:\Users\Lenovo\OneDrive\sovereign-infra` | private git repository | the evidence plane, the ops ledgers, the agent runtime, the governance record, the design system, the operational SQLite store, the lander |
| `thesis-db` | `...\Final Master Thesis` | not a repository, desktop only | `_DATABASE\csv_exports` (the source CSVs), `_GOVERNANCE` (decision log, asset register, provenance manifest) |

**Rule FS-1.** `C:\Users\Lenovo\sovereign-infra` is **not** the repository. It is
an empty stub and five consecutive sessions read its emptiness as a failed
mount. L-143. The registry declares it as a decoy and
`scripts/build_data_map.py` refuses to resolve a root that carries no signature
file, so the decoy now fails to resolve rather than resolving to nothing.

**Rule FS-2.** The thesis database is **desktop only** and is not reachable from
a GitHub runner. Anything measured there is desktop plane evidence and says so.
A control that requires it must degrade with a stated cause rather than report
zero. D-007: withheld with cause, never imputed.

**Rule FS-3.** A folder whose name matches a root is not therefore that root.
Identity is established by a declared signature file, never by a name:
`data/qesis_v8.json` for qesis-mcp, `ops/GOVERNANCE.md` for sovereign-infra,
`_DATABASE/csv_exports` for thesis-db.

## 2. Generated versus hand maintained

The most common structural defect in this ecosystem is a hand-maintained file
sitting in a generated namespace, or a generated file with no live generator.
Both drift silently, because nothing is positioned to notice.

**Rule FS-4.** Every generated artefact carries a `generator` field naming the
script that writes it, and **that script exists and runs**. A generator field
naming a script that does not exist is a hand-maintained artefact wearing a
generator's name. `data/DATA_MAP.json` carried exactly that from 2026-08-14 to
2026-08-28: it named `scripts/build_data_map.py`, which did not exist, and by
the time anyone checked, six of its fifteen critical entries no longer matched
the bytes on disk.

**Rule FS-5.** Every generated artefact has a `--check` mode wired into
`qesis-integrity.yml`, so a stale copy fails the build rather than misleading a
reader. `build_graph.py`, `build_eval.py`, `build_landing.py`,
`build_ecosystem_state.py`, `build_percolation_block.py`, `self_exposure.py`
and `build_data_map.py` all hold this contract.

**Rule FS-6.** A hand-authored document is never written into a generated
directory. `ops/reports/<YYYY-MM-DD>.md` is the runner's output namespace: a
hand-written file there is overwritten by the next cron and, worse, presents
authored content as measured. Session and agent reports go to
`ops/<AGENT>_<TOPIC>_<YYYY-MM-DD>.md` or
`ops/reports/<AGENT>_<TOPIC>_<YYYY-MM-DD>.md`, which the date-named glob does
not collide with.

### The two namespaces, stated

| Namespace | Kind | Writer |
|---|---|---|
| `data/*.json`, `data/axes/*.json`, `eval/`, `public/index.html`, `public/blueprint.html` | generated | the named build script, only |
| `ops/ECOSYSTEM_STATE.json`, `ops/PATH_REGISTRY.json`, `ops/RDL_LADDER.json`, `ops/SELFHEAL_LATEST.json`, `ops/AUDIT_REPORT.md`, `ops/CI_LAST_FAILURE.md`, `ops/reports/<date>.md` | generated | the named build script, only |
| `ops/LESSONS_LEDGER.md` | append only, machine written | `scripts/rdl.py record` and `scripts/rdl_append.py`, never a text editor |
| `ops/D-NNN_*.md`, `ops/GOVERNANCE.md`, `ops/*_REGISTER.md`, `CLAUDE.md`, `SESSION_START.md` | hand maintained, governed | a human or an agent, by edit |

## 3. Naming conventions for ops documents

**Rule FS-7.** One shape per kind, and the shape says what the document is
before it is opened.

| Kind | Shape | Example |
|---|---|---|
| Decision | `D-NNN_SHORT_TITLE.md`, number allocated from the highest existing `D-` and never reused | `D-118_AGENTIC_OBSERVABILITY.md` |
| Governance clause | `G-NN_SHORT_TITLE.md` | `G-07_AUTONOMOUS_REMEDIATION.md` |
| Register, append only | `SHORT_NAME_REGISTER.md` | `SOURCE_ACQUISITION_REGISTER.md` |
| Runbook | `SUBSYSTEM_RUNBOOK.md` | `POSTGRES_RUNBOOK.md` |
| Generated daily report | `reports/YYYY-MM-DD.md` | `reports/2026-08-27.md` |
| Session or agent report | `[reports/]AGENT_TOPIC_YYYY-MM-DD.md` | `reports/ARCHITECT_FILESYSTEM_2026-08-28.md` |
| Handover | `HANDOVER_YYYY-MM-DD.md` | `HANDOVER_2026-08-26.md` |
| Pending workflow, awaiting a human click | `pending_workflows/<name>.yml` | `pending_workflows/gcp-trigger-disconnect.yml` |

**Rule FS-8.** A document that describes a vintage names that vintage in its
text, or it is deleted. L-074. `ops/D-103_STATUS.md` is currently the open case:
it describes a release that had not happened when it was written and v8.6
superseded it.

**Rule FS-9.** A `.ps1`, `.bat` or `.txt` operator script does not live in
`ops/`. `ops/` is the record. Executables live in `scripts/`, and the one file
the operator double-clicks lives in the `sovereign-infra` root. There are
currently seven `.ps1` and one `.txt` in `qesis-mcp/ops/` that violate this and
the reorganisation plan proposes their move.

## 4. The reachability rule. This is the load-bearing clause.

**Rule FS-10.** **A file named in `lineage.sources` of the served index must be
reachable from `data/DATA_MAP.json`, or the citation is a defect.**

Not a warning, not a note. A defect, in the citation, gated at build time.

The reasoning. `data/qesis_v8.json` cites two source files by SHA-256 as the
provenance of every number it serves:

| Cited file | Declared SHA-256 | Bytes | Lives in |
|---|---|---|---|
| `v8_qesis_country_scores.csv` | `022e4f0bfbb5e064f49d6203107bdf6729b718854ec26fa3c648a68eb518a121` | 8516 | `thesis-db/_DATABASE/csv_exports/` |
| `cloud_regions_master.csv` | `44d203ae4322b829f7a13e00abc5c722d87b008ffd9fd437d8b7b5cc54a8a423` | 114774 | `thesis-db/_DATABASE/csv_exports/` |

Neither is in either repository. Both were verified byte for byte against their
declared hashes on 2026-08-28 and **both reproduce exactly**. The data is sound.
What was absent until now is a control that says so, and an unverified true
claim is indistinguishable from an unverified false one at the moment a reader
meets it.

The rule is enforced by two gates in `scripts/build_data_map.py`:

- **DM-1** every key of `lineage.sources` appears in `critical_sources` with at
  least one location, or the run fails. Where the root is out of reach, the
  finding is `unreachable` with its cause and the gate withholds rather than
  failing, because a runner that cannot see the desktop has learned nothing
  about the desktop.
- **DM-2** where the file is reachable, its bytes reproduce the declared
  SHA-256, or the run fails.

**Rule FS-11.** A path is written as **logical root plus repository-relative
path**, never as an absolute path. `data/DATA_MAP.json` as generated on
2026-08-14 recorded its roots as `/sessions/trusting-brave-fermat/mnt/...`,
which belongs to one sandbox session and is dead in every other one, including
the session that later read it. Gate **DM-3** refuses any emitted document
containing an absolute path marker or a `/sessions/` fragment, and its refuse
fixture is the 2026-08-14 document exactly as it stood.

**Rule FS-12.** Content is compared by SHA-256 and byte count, never by
modification time. A git checkout resets mtime and OneDrive hydration sets mtime
to the moment of first read, so an mtime records when a filesystem touched a
file and never records whether its content changed.

**Rule FS-13.** A script resolves a data file through `DATA_MAP.json` or through
a repository-relative `ROOT / "data" / ...` expression. A literal absolute path
in a script is a future instance of the same defect. The one legitimate
exception is the **declaring authority**: `scripts/build_ecosystem_state.py`
writes `PATH_REGISTRY.json` and must therefore hold the literals, because a
bootstrap cannot read the file it is about to write. Every other literal is a
copy of that declaration and drifts from it.

## 5. Moving a file is an Article 14 act

**Rule FS-14.** A file move breaks the paths gates and scripts depend on.
Reorganisation is therefore **proposed, never executed** by an agent. The
proposal lists source path, destination path and reason for every file, plus the
call sites that must change in the same change set. The operator signs. See
`ops/FILESYSTEM_REORG_PLAN_2026-08-28.md`.

**Rule FS-15.** Where a move is approved, it lands with its call-site changes in
one change set, in both repositories where G-01 applies, each on its own
explicitly created branch. A move landed without its call sites is a broken
build with a tidy directory listing.

---

## 6. What this standard does not do, stated before it is asked

It does not make the ecosystem tidy. Tidiness is not the objective and pursuing
it would cost more than it returns: roughly ninety `ROOT / "data" / "x.json"`
expressions across `scripts/` are repository-relative, portable and correct, and
rewriting them to route through `DATA_MAP.json` would add a dependency, a
failure mode and a lookup to code that has none of the three today. They are not
listed as defects here and they are not defects.

It does not make a stale map correct. It makes a stale map **loud**. The gate
fails the build; it does not repair the citation.

It does not reach the thesis database from CI, and no configuration can. That
root is desktop only by construction, and a control that pretends otherwise
would report zero where it should report withheld.
